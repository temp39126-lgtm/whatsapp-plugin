# Production security

This document describes the security controls built into the WhatsApp CRM stack.

## Reverse proxy (Caddy)

Production deploys use **Caddy** as the reverse proxy (`deploy/Caddyfile`):

- Automatic HTTPS via Let's Encrypt
- Routes `/api/*` and `/socket.io/*` to the Express backend
- Routes all other traffic to the Next.js frontend
- Gzip + zstd compression at the edge
- Security headers: HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`
- HTTP keep-alive to backend services

The backend sets `trust proxy` in production so rate limiting and logs use the real client IP from `X-Forwarded-For`.

## Rate limiting

| Layer | Scope | Default limit |
|-------|--------|---------------|
| Global API | All `/api/*` routes | 200 requests / 15 min per IP |
| Auth | Login, signup, forgot/reset password | 20 requests / 15 min per IP |
| Webhooks | Meta WhatsApp webhook POST | 500 requests / min per IP |

Configure via environment variables:

- `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX`
- `AUTH_RATE_LIMIT_WINDOW_MS` / `AUTH_RATE_LIMIT_MAX`

## Injection prevention

### NoSQL injection

- **Zod validation** on request bodies and query params
- **`express-mongo-sanitize`** strips `$` and `.` operators from user input
- **`mongoose.strictQuery: true`** rejects unknown query operators
- **Regex escaping** on all user-provided search strings used in `$regex` queries (contacts, conversations)

### SQL injection

Not applicable — the application uses MongoDB (NoSQL), not SQL.

## Input validation

All API endpoints use Zod schemas via `validateBody` / `validateQuery` middleware. Invalid input returns HTTP 400 before reaching business logic.

## Authentication & authorization

- JWT-based auth with bcrypt password hashing
- Role-based access control (ADMIN / USER)
- Permission checks on sensitive routes (analytics, settings)
- Tenant isolation on all data queries

## HTTP security headers (Helmet)

The Express backend applies Helmet middleware with settings tuned for Socket.io and media serving.

## Database indexes

Indexes are defined on Mongoose schemas and synced on startup via `syncIndexes()`. Key indexes:

| Collection | Indexes |
|------------|---------|
| Conversation | tenant + status, assigned user, last message, unread count |
| Message | conversation + createdAt, tenant + direction + createdAt |
| Contact | tenant + phone, tenant + name, tenant + updatedAt |
| Call | tenant + createdAt, tenant + status, tenant + direction |
| InternalNote | tenant + conversation + createdAt |

## Caching

In-memory TTL cache (default 60 seconds) for:

- Analytics dashboard metrics (per tenant)
- Tag lists (invalidated on create/update/delete)

Configure TTL via `CACHE_TTL_MS`. For multi-instance deployments, consider Redis.

## Webhook security

- Meta webhook signature verification (`X-Hub-Signature-256`)
- Dedicated rate limiter on webhook endpoint
- Verify token check on webhook subscription

## Secrets & encryption

- `JWT_SECRET`, `ENCRYPTION_KEY`, and S3 credentials via environment variables
- WhatsApp app secrets encrypted at rest with AES-256
- Production secrets generated by `scripts/generate-deploy-secrets.sh`

## Production checklist

1. Set strong `JWT_SECRET` and `ENCRYPTION_KEY` (use the deploy script)
2. Set `NODE_ENV=production`
3. Configure `CORS_ORIGIN` and `FRONTEND_URL` to your domain
4. Use HTTPS only (Caddy handles this automatically)
5. Keep MongoDB and MinIO off the public internet (Docker internal network)
6. Set `ADMIN_EMAIL` / `ADMIN_PASSWORD` for the initial admin account
7. Configure Meta webhook verify token and app secret

## Reporting issues

If you discover a security vulnerability, please report it privately to the repository owner rather than opening a public issue.
